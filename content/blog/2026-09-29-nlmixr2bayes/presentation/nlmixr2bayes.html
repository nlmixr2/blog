nlmixr2bayes: Stan, without rewriting your model

On behalf of the nlmixr2 team

This is nlmixr2 bayes. A Stan interface for nlmixr2 – and, as the hex says, powered with Stan rather than replacing it.

This talk, in three pictures

Three things I will talk about today

1. Link the likelihood, don’t translate the model

So let’s start with what the package actually does.

Until now, going Bayesian meant maintaining the model twice

Can you do Bayesian estimation? This is a common question I get.

Until now the answer was not yet. For now you have to write it again in Stan. Hand code the model with Torsten, or if you have NONMEM move it over to NONMEM’s bayes methods.

Either way you end up maintaining two models. The nlmixr2 one, and the Stan one.

And when those two disagree, you had to figure out why.

Stan does not need your model – it needs your likelihood

Here is the idea the whole package rests on.

Stan does not actually need your model. It needs a log density and a gradient.

So rather than translate the model into Stan’s language, we link Stan to the likelihood that already exists. We keep our own ODE solving and dose handling and individual likelihoods. Stan calls the compiled model as an external function, and gets the analytic gradients handed to it.

Stan still owns the parts that are genuinely Bayesian – the priors, the eta hierarchy, and the sampler itself.

One model. One likelihood. One source of truth.

Priors are declared next to the parameters they describe

one.cmt <- function() {
  ini({
    tka <- 0.45
    tcl <- log(c(0, 2.7, 100))
    tv <- 3.45
    add.sd <- c(0, 0.7)
    eta.ka ~ 0.6; eta.cl ~ 0.3; eta.v ~ 0.1
    prior(tka) ~ dnorm(0.45, 1)
    prior(tcl) ~ dnorm(1, 1)
    prior(tv) ~ dnorm(3.45, 1)
    prior(add.sd) ~ dcauchy(0, 2.5)
  })
  model({ ... })
}

All 39 real-valued distributions in the lotri catalog – and the catalog is deliberately one-to-one with Stan’s, so dcauchy() means what Stan means by it. lotri::lotriPriorDists() lists them.

This is the standard toy model with the four new prior lines.

Priors are right next to the parameters they describe, in the same syntax as everything else in the initialization block.

The distribution catalog is deliberately one to one with Stan’s – all thirty nine real valued distributions.

est="nuts" gives back an ordinary nlmixr2 fit

fit <- nlmixr2(one.cmt, theo_sd, est="nuts",
               control=nutsControl(seed=42, chains=2, iter=1000))
print(fit)
#> -- nlmixr2 Stan (HMC) (2 chains x 500 draws; max Rhat 1.009; min ESS 377) --
#>         Est.     SE %RSE Back-transformed(95%CI) BSV(CV%) Shrink(SD)%
#> tka    0.469  0.222 47.4       1.60 (1.03, 2.47)     92.9       17.1
#> tcl     1.01  0.103 10.2       2.75 (2.24, 3.36)     32.8       20.4
#> tv      3.45 0.0524 1.52       31.5 (28.5, 35.0)     17.2       26.1
#> add.sd 0.707 0.0544 7.69    0.707 (0.601, 0.814)

"nuts" names the algorithm, the way "foce" and "focei" do – IPRED, CWRES, plot(fit) and the rest work, because the fit object does not know Stan produced the numbers.

Fitting is one call. The estimation method is nuts.

Nuts names the algorithm – Stan’s no U turn sampler – rather than the software tool.

And what comes back is an ordinary nlmixr2 fit object. The sampler diagnostics are in the header, the posterior is summarized in the usual par fixed table with all the other features of a nlmixr2 fit

A model with no priors is refused – and the error is the fix

nlmixr2(noPriors, theo_sd, est="nuts")
#> Error: no priors declared; add prior() lines to ini({}), e.g.
#>   prior(tka) ~ dnorm(0.45, 1)
#>   prior(tcl) ~ dnorm(0.993, 1)
#>   prior(tv) ~ dnorm(3.45, 1)
#>   prior(add.sd) ~ dcauchy(0, 2.5)

Bayesian output built on silently-invented priors looks every bit as publishable as the real thing, and is wrong.

The one default is on omega blocks – lkj_corr_cholesky(2) on the correlation, half-Cauchy on each SD – and even that is announced in a message rather than assumed quietly.

Note that a model with no priors errors.

However, the error message suggests prior lines to put in your initialization block, derived from the model’s own starting values and bounds.

The one place we do supply a default is on the omega blocks which will be announced when running the fit

2. What linking buys you

Now, what does linking Stan to nlmixr2 actually buy you?

Stan’s ODE interface cannot express a dose

This provides dose handling for pharmacometrics datasets. No more hand-coding stan. Not only that, it is tested by everything that our package has been using for years

Delay differential equations are ordinary models here

model({
  ...
  d/dt(R) <- kin - kout * delay(R, tau)   # tau is estimated like any theta
})
  • Stan has no DDE solver at all – and never needs one, because it never sees the ODE system
  • rxode2 switches to a dense solver behind the likelihood, exactly as it does under focei or saem
  • The same is true of M2/M3/M4 censoring, the residual-error catalog, linCmt() closed forms, mu-referenced covariates and estimated boxCox() lambda

One of the other consequences is that if you have a new feature in nlmixr2 it is inherited in stan.

For example, the new delay differential equations can now be expressed in stan with this linkage, something you couldn’t do in stan at all without this linkage.

The same argument covers the censoring machinery, the residual error catalog, and the closed form solved solutions. None of that needed special handling on the Stan side. It was already in the likelihood.

Linked, the same model draws 2.4x more effective samples per second

native Stan nlmixr2bayes (linked)
wall clock 142.7 s 80.8 s
worst bulk ESS 236 286-378
worst ESS / s 1.66 4.04
gradient evaluation 1.98 ms 1.36 ms (C level)
posterior means agree to < 0.01 on every parameter

Three things get it there: chains run in forked processes (draws bit-identical to a sequential run); the whole gradient comes from one solve per subject; and Omega^-1 is rebuilt on the C side instead of by evaluating an R closure every single evaluation.

I did not expect this result, so let me be clear about what is being compared. This is the same model, with the same priors, fitted two ways: once as a hand written native Stan program, and once linked.

The posterior means agree to better than a hundredth on every parameter. So we are comparing two routes to the same answer.

The linked run is about twice as fast in wall clock, and – more importantly – it extracts more effective samples per draw. Put together, that is two point four times the effective samples per second.

Three things got it there. The chains run in forked processes, and those draws are bit identical to a sequential run.

Parallelism has two axes, and neither one is Stan’s threading

A word on parallelism, because it works differently here.

We deliberately do not engage Stan’s threading. Layering Stan’s threading runtime on top of our own would just have the two of them contend with each other for the same cores.

So there are two axes instead. By default, on unix, the chains run in forked processes.

Or, if you set chain cores to one, the chains run sequentially and each individual likelihood evaluation is split across threads by subject instead.

Either way the O-D-E solve is the rate limiting step in a pharmacometric model, so that is where the cores go.

ADVI and Pathfinder are the fast first look, not the answer

fitAdvi <- nlmixr2(one.cmt, theo_sd, adviControl(seed=42))
fitPf   <- nlmixr2(one.cmt, theo_sd, pathfinderControl(seed=42))
  • Same generated program, same linked likelihood
  • 3-10x faster; ADVI about 30-40 s, Pathfinder about 90 s here
  • Passing the control is the est=, the way foceControl() implies est="foce"
  • ADVI understates tails and posterior correlations
  • Pareto k-hat replaces Rhat and ESS on those fits
  • k-hat above 0.7 warns; hierarchical PK posteriors routinely exceed it

The same generated program and the same linked likelihood also run Stan’s variational approximations, and multi path Pathfinder.

Each one has its own control object and each runs a separate estimation routine.

These are three to ten times faster. On this model, add vee finishes in about thirty to forty seconds.

But add vee is an approximation, and it understates tails and posterior correlations. So treat these two as the fast first look, and treat NUTS as the answer.

The posterior is right there, and so is the stanfit

fit$posteriorSummary   # exact quantiles
fit$objDf              # FOCEi, WAIC, LOO rows
fit$stanCode           # the generated program
sf <- fit$stanfit      # rstan::stanfit
rstan::traceplot(sf, pars="tka")
bayesplot::mcmc_pairs(sf, ...)
  • $parFixed CIs are a Wald approximation – for SDs and small omegas quote the exact quantiles instead
  • WAIC and LOO are leave-one-subject-out: the subject is the exchangeable unit
  • Declared Stan parameters read like your model – tka, add_sd, sd_eta_ka

Beyond the usual accessors, the fit carries the posterior itself.

Two things worth knowing. The confidence intervals are a Wald approximation built from the posterior covariance, so for anything skewed – standard deviations, small omegas – you want the exact quantiles from posterior summary instead.

And the typical bayesian statistics are leave one subject out, not leave one observation out, because the subject is the exchangeable unit of a hierarchical model.

The whole R Stan fit object is kept, so trace plots, bayesplot, posterior, and the rest of that ecosystem all work unchanged.

3. Is it right?

Which brings me to the validation section

Every claim is checked against something that shares no code with it

check agreement
Stan’s assembled gradient vs. Richardson finite differences ~3e-8
d/d(eta), d/d(theta) vs. central differences of the conditional ~3e-8
quadrature marginal vs. est="agq" at nAGQ=101 3e-7
censored M2/M3/M4 and ll() vs. hand-computed textbook densities exact
prior-only sampling vs. every declared prior one-sample KS each
full posterior vs. a hand-written native-Stan implementation within 3x MCSE
the linked likelihood engine itself NONMEM-validated upstream

Because the bridge works at the likelihood level, the checks have to be at the likelihood level too.

These are the independent ones – each is a check against something the bridge shares no code with.

And underneath all of it, the linked likelihood engine is the one already validated against NONMEM upstream in nlmixr2.

What is in scope is stated, and everything else is refused

  • mixed and population-only (single-subject) models
  • ODE, DDE and linCmt()
  • censoring, the residual catalog, user ll() endpoints
  • mu-referenced and non-mu etas; mu-referenced covariates, fixed or time-varying
  • estimated alag/f/dur/rate, estimated Box-Cox lambda, IOV, 2-component mix()

Refused with an explanation

  • mixtures beyond two components, for now

  • the 8 discrete distributions

Deliberately first-order: no Riemannian HMC, no embedded Laplace. NUTS, ADVI, Pathfinder and optimization are all first-order anyway.

Here is the scope, stated plainly.

Supported: mixed and population only models, differential equations, delay differential equations, closed form models, censoring, the residual catalog, user written likelihoods, inter occasion variability, and two component mixtures.

Refused, with an explanation rather than a silent approximation: mixtures beyond two components for now, and the discrete distributions.

The bridge is also deliberately first order, which rules out some specialized Stan models.

If you already have an nlmixr2 model, you already have the Bayesian one

pak::pak("nlmixr2/nlmixr2bayes")
  • Add prior() lines to ini({})
  • Change est="focei" to est="nuts"
  • That is the whole migration
  • The posterior is sampled against the identical likelihood code your FOCEi run used
  • “What does the Bayesian version say?” becomes a question about the data and the priors
  • Not about whether you translated the model correctly

So, to close.

If you have an nlmixr2 model you already trust, adding prior lines changes the model to a bayesian one.

Which means that, for the first time, when you ask what does the Bayesian version say, you don’t have to worry about your model being translated correctly.
